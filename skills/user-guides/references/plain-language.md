# Plain language — vocabulary tiers, formatting, tone checks

Plain language has an international standard: [ISO 24495-1:2023](https://www.iso.org/standard/78907.html). It defines plain language as communication whose wording, structure and design let intended readers **easily find what they need, understand it, and use it** — three tests worth applying to any guide you're unsure about. The standard is paywalled; the [International Plain Language Federation](https://www.iplfederation.org/iso-standard/) publishes a free summary. What follows is how those principles land in a help centre.

## The four vocabulary tiers

Every word in a help centre falls into one of four tiers. Which words go in which tier is a product fact — ask for it; the tiers and the judgment are the standard. The examples below set the pattern — apply the same judgment to similar words.

1. **Prefer — plain everyday words.** The default register, whatever the product: send, save, share, delete, turn on · account, sign up, log in · question, chance, likely. Where a plain word and a formal one mean the same thing, the plain one wins every time.
2. **Use freely and gloss on first use — the product's own domain terms.** The vocabulary readers meet in the interface and across the space: _version history, permissions, workspace_ in a collaboration tool; _claim, excess, policyholder_ in insurance; _dose, refill, prescriber_ in a pharmacy app. Use the real word — hiding it behind a vague substitute leaves readers unprepared when they meet it on screen — but explain it plainly the first time: "your excess — the part of a claim you pay yourself." Only swap in a plainer word when the domain term adds nothing.
3. **Use only when required, and explain plainly the first time.** Terms naming something the reader must actually see, tap or do, even though the word is technical — choosing a file format before an export, granting a permission, picking a sync frequency. Never assume they already know it.
4. **Avoid unless genuinely unavoidable.** Behind-the-scenes plumbing the reader never touches — _webhook, replication lag, hashing, middleware, our event pipeline_ — and all marketing language ("revolutionary", "democratizing", "empowering"). If a plumbing term genuinely surfaces, describe what it does rather than leaning on the label: "we check with your bank" beats "we call the issuer authorization endpoint."

The test separating tiers 3 and 4 is **teach-or-cut**: would a first-time user need this word to complete the task or understand the answer? Yes → tier 3. No → tier 4, cut it.

## Formatting

- **Numbered lists** for steps that happen in order; **bullets** for parallel options or a short set of points.
- **Bold** for button names, menu labels, and inline warnings only — not for emphasis everywhere.
- **Headings for scanning:** one title, H2 sections, H3 sub-steps. Don't stack everything as top-level headings.
- **Screenshots** when they help a reader find or confirm something in the app, with a short caption. No decorative images.
- **Show the arithmetic behind any number the reader is asked to accept** — a charge, a limit, a quota, a deadline, a storage allowance. Readers trust what they can see. Walk through a plain worked example first ("a 2% fee on a $50 order is $1"; "50 GB holds roughly 15,000 photos"), put any actual formula after the plain explanation and label it clearly, and never let the formula be the first thing a beginner hits. If the full calculation is long, summarize plainly and link the detail.

## Tone checks

- Read the first line alone. Does it answer the question? If not, rewrite it.
- Read it aloud. If you run out of breath, the sentence is too long.
- Would someone who has never used a product like this understand every word? If not, simplify or define.
